# ADR-0013: The network API

Status: accepted (after 0.1.19, unreleased). The API-key, plain-HTTP and Settings-card parts were replaced before release by ADR-0014: a server has a name and an optional password, the network connection is encrypted (TLS with a fingerprint the client confirms), servers announce themselves on the network, and hosting lives in a panel beside the window. What is written below about the requests, the HTTP server, the limits and the visibility of uploads still holds; read "key" as "password" and ignore "No TLS".

## Context
Features.md asks for "the ability to run a local AI server like LM Studio". The owner's answer to what that means: the app serves a local API that other programs can call, on this computer and over the network. Link transcription (yt-dlp) is a separate step; the API takes recordings.

## Decision
- **Off by default, switched on in Settings → Network API**, with a port (default 8642), a key and *Allow other computers on the network*. The server runs only while the app is open; there is no background service. Without the network option it listens on `127.0.0.1` only; with it, on every address (IPv6 dual-mode where available). The first time, Windows may ask whether to let the app through its firewall.
- **Every request but two needs the key.** `GET /` (a text page) and `GET /v1/health` are open so that a client can tell the server is there; everything else, including unknown paths, answers 401 without a valid `Authorization: Bearer <key>` or `X-Api-Key`. The key is never accepted in the address (it would end up in logs and history). It is 44 characters from 40 random draws from an alphabet of 57 letters and digits, made when the API is first switched on, shown masked, copied with a button and replaced with *New key* (the old one stops working at once). It is compared in constant time. After 8 wrong keys from one address in a minute that address is refused for a minute, even with the right key. Browsers cannot reach the API from a web page: a request with an `Authorization` or `X-Api-Key` header needs a preflight, which is answered with 405 and no CORS headers.
- **The key is stored in `settings.json`, in clear**, like every other file the app keeps (the privacy policy already says nothing is encrypted); anyone who can read the user's files can read it, and could read the transcripts too.
- **No TLS in this version.** The connection is plain HTTP and the key travels in clear on the network. The settings card and the policy say so: use the network option only on a network you trust (or through a VPN or a reverse proxy). TLS with a self-signed certificate would make every client pass `-k`, so it was left for a later step that can also generate and pin a certificate.
- **An own small HTTP/1.1 server** (`LocalHttpServer`, `TriAsr.Infrastructure`), because `HttpListener` needs an administrator or a URL reservation to listen on the network, Kestrel would add the ASP.NET Core runtime to a self-contained app, and the architecture rules allow no new package. One request per connection (`Connection: close`); request bodies of a known length or chunked; `Expect: 100-continue` is answered only when the handler starts reading, so a refused upload (wrong key) is never sent; bodies stream from the connection to disk. Limits: headers 16 KB and 15 s, body 8 GiB and 60 s of silence, 32 connections, 100 headers; strict parsing (CRLF only, no repeated `Content-Length`, no `Content-Length` with `Transfer-Encoding`) so that nothing can be smuggled past it. The handler never maps a path to a file. `MultipartReader` reads `multipart/form-data` as a stream for the OpenAI-style endpoint.
- **The API sees only what was sent through it.** Uploads are saved in `Api/Incoming/<guid>/<safe name>` under the data folder and become ordinary projects (listed under Projects, kept until the user deletes them); a job whose source is outside that folder is invisible to the API (404). A client cannot read the user's other projects. Error messages hide the folder of the upload (`<uploads>`).
- **One recording at a time**, through the same pipeline as the window's own jobs and the watch folder: the pipeline serialises them, an API job does not move the user's selection in Projects, and while one runs, model downloads, tuning and setup are blocked (`SetupBusy`). The API's own queue waits (up to 50 recordings) while those operations are running. Recordings still waiting when the app is closed are picked up again the next time the API is switched on; one that was running becomes *cancelled*.
- **Requests**: `POST /v1/transcriptions?language=&name=` with the recording as the body (`202`, `Location`); `GET /v1/transcriptions`, `GET /v1/transcriptions/{id}` (`?wait=30` holds the answer until the end), `GET .../transcript?format=json|txt|md|srt|vtt|csv|docx|full-json&mode=strict|readable`, `POST .../cancel`; `GET /v1/languages`, `GET /v1/models`; and the OpenAI-compatible `POST /v1/audio/transcriptions` (multipart form, `response_format` json, text, srt, vtt or verbose_json, answered when the transcript is ready) so that tools written for that API work with the base URL `http://127.0.0.1:8642/v1`. Subtitle formats answer 422 for a Canary-only transcript (no native timestamps), as the window's export does. Errors are `{"error":{"code","message","type"}}`; the codes are for programs and stay in English.
- **Texts**: the Settings card is translated like every other text; the program text of the example commands is not.

## Limits
Works only while the app is open; one recording at a time; no deletion of projects through the API (data is deleted in the window); no streaming/live transcription; no recording given as a link yet; no TLS; the transcript endpoints return the saved review (manual edits included), not the raw engine output.

## Verification
Unit tests drive `LocalHttpServer` over real sockets (malformed and oversized requests, chunked bodies, slow clients, stalled uploads, `Expect: 100-continue`, connection limit, one port per server) and `MultipartReader` (boundaries split across reads, binary look-alikes, 6 MB part). `ApiServiceTests` run the whole API over a real socket with fake engines (keys, throttle, every format, ordering, cancel, resume, visibility, safe names, error text, the OpenAI-style form). `ApiSettingsTests` cover the window's side (off by default, restored from settings, key made and replaced, bad and busy ports, language). `scripts/api-smoke.ps1` runs the real flow with the real engines: a recording sent over HTTP is transcribed (the transcript is the spoken sentence), fetched as text, JSON and subtitles, sent again through the OpenAI-style form, and one sent and cancelled; wrong or missing keys are refused and the window's selection does not move.
